# Руководство разработчика — Pocket Option Background

**Версия документа:** 1.0  
**Версия приложения:** 0.1.1  
**Стек:** Electron, Node.js, HTML, CSS, JavaScript  
**Целевая платформа первой версии:** Windows 11 x64  
**Статус реализации:** исходный код создан; установка зависимостей, запуск на Windows 11, интеграция с актуальным DOM Pocket Option и сборка установщика ещё должны быть проверены.

## 1. Обзор архитектуры

Pocket Option Background — отдельное Electron-приложение в каталоге `Pocket-Option-Background/`. Оно не является браузерным расширением и не встраивает существующее торговое ядро.

Архитектура разделена на три зоны:

1. **Main process (`main.js`)** — окна, жизненный цикл, трей, настройки, журналы, мониторинг, восстановление, обновления и IPC.
2. **Renderer processes (`renderer/`)** — пользовательская панель и мини-виджет. Node.js API напрямую им не предоставляется.
3. **Интеграция сайта (`site-preload.js`, `site-bridge.js`)** — DOM-адаптер баланса и data-only наблюдатель рыночных WebSocket-событий.

Обмен между renderer и main организован через `preload.js` и `contextBridge`.

## 4. Окна и жизненный цикл

### Главное окно

- Размер при создании: 1180×820; минимальный: 980×680.
- Загружает локальный `renderer/index.html`.
- Использует `preload.js`, `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`.
- Событие закрытия перехватывается: пока приложение не завершает работу, окно скрывается.

### Окно Pocket Option

- Размер при создании: 1440×940; минимальный: 980×680.
- Использует persistent partition `persist:pocket-option-background`.
- Загружает URL из `ACCOUNT_URLS`.
- Использует `site-preload.js`, отключённый background throttling и ограниченную обработку внешних ссылок.
- Закрытие окна скрывает его, сохраняя процесс приложения и профиль сессии.

Внешние HTTP(S)-ссылки из popup handler направляются в системный браузер через `shell.openExternal`; создание отдельного popup-окна запрещается.

### Мини-виджет

- Размер: 270×154; минимальный: 250×140.
- Прозрачное frameless окно, перемещаемое и изменяемое по размеру.
- `alwaysOnTop: false`, `skipTaskbar: true`.
- Использует общий `preload.js` и локальный `widget.html`.

### Системный трей и single instance

Main process создаёт системный трей и блокирует повторный экземпляр через `app.requestSingleInstanceLock()`. При повторном запуске существующее приложение показывает главное окно. Закрытие всех окон не завершает приложение: оно остаётся в трее. Полный выход проходит через `before-quit`.

Автозапуск Windows в текущей версии не реализован.

## 5. Безопасность Electron и IPC

Renderer не получает прямой доступ к Node.js. В `preload.js` через `contextBridge.exposeInMainWorld` публикуется ограниченный объект `window.pocketApp`.

Основные методы API:

| Метод | Назначение |
|---|---|
| `getStatus()` | Получить публичный статус приложения |
| `launchSite()` / `showSite()` / `hideSite()` / `reloadSite()` | Управление окном сайта |
| `switchAccount(mode)` | Запрос переключения DEMO/REAL |
| `toggleWidget()` | Показать/скрыть виджет |
| `getSettings()` / `saveSettings(value)` | Чтение и сохранение настроек |
| `runCheck()` | Запуск полной диагностики |
| `readLogs()` / `exportLogs()` | Чтение и экспорт журналов |
| `checkUpdates()` / `downloadUpdate()` / `installUpdate()` | Управление обновлением |
| `onStatus(fn)` / `onLog(fn)` / `onCheckResult(fn)` | Подписка на события main process |

Не добавляйте в preload универсальный IPC send/invoke, произвольный доступ к файловой системе или shell. Для каждой новой операции создавайте отдельный метод с проверкой аргументов на стороне main.

### Проверка сообщений от сайта

В main process события `site:balance`, `site:log` и `site:market-batch` принимаются только если sender совпадает с `siteWindow.webContents`, а URL отправляющего frame принадлежит `pocketoption.com` или его поддомену. Market batch дополнительно ограничен allow-list событий, размером и частотой через core/ipc-validation.js. Баланс проверяется по типу, диапазону, свежести timestamp и частоте. Сообщения из MAIN world остаются недоверенными данными и никогда не должны трактоваться как команды.

Payload баланса дополнительно проверяется: тип счёта должен быть `demo` или `real`, баланс — конечное неотрицательное число, timestamp должен быть свежим и не находиться в будущем; сообщения ограничиваются по частоте. Это не устраняет возможность подделки same-origin скриптом страницы, поскольку текущий баланс передаётся через window.postMessage. Для полной защиты требуется перейти на чтение DOM из isolated preload или принять отдельное архитектурное решение.

## 6. Интеграция с DOM Pocket Option

Интеграция состоит из двух уровней.

### `site-bridge.js`

Скрипт внедряется в страницу сайта из main process после загрузки и при готовности DOM.

Он:

- ищет элементы баланса по CSS-селекторам;
- проверяет видимость и состояние элементов;
- нормализует текстовые значения в число;
- определяет DEMO/REAL по DOM-элементам и признакам активного режима;
- сохраняет диагностический объект `window.__PT_PO_STATUS__`;
- отправляет `PT_PO_BALANCE` через `window.postMessage`;
- использует `MutationObserver` и периодический опрос раз в секунду;
- отправляет баланс при изменении или не реже одного раза в 5 секунд, пока данные доступны.

Текущие селекторы являются эвристическими и основаны на селекторах, использованных в коде расширения проекта версии 3.6.0. Они не являются официальным API Pocket Option.

### `site-preload.js`

Слушает сообщения только от того же window и того же origin. Сообщения с типами `PT_PO_BALANCE` и `PT_PO_LOG` проверяются и передаются в main через IPC. На document-start через `webFrame.executeJavaScript` устанавливается наблюдатель WebSocket в MAIN world. Он наблюдает только события `updateAssets`, `updateStream`, `quotes/stream`, `updateHistoryNewFast`, `updateHistoryNew`, `loadHistoryPeriod`, `loadHistoryPeriodFast` и `history/list/v2`; пакетирует их в `PT_PO_MARKET_BATCH`. Он не отправляет сообщения в WebSocket и не взаимодействует с торговыми кнопками. Фактическая установка до первого сокета и актуальные payload должны быть подтверждены runtime-тестом.

### Свежесть данных

Main process считает баланс устаревшим, если последнему подтверждению более 15 секунд. Для успешного переключения счёта main ждёт до 20 секунд, пока `window.__PT_PO_STATUS__` не подтвердит требуемый режим и ненулевой факт наличия значения баланса (само значение может быть 0).

**Обязательное тестирование перед релизом:** проверить текущую разметку Pocket Option, валюты и локали чисел, оба режима счёта, скрытые/выпадающие элементы баланса, обновление баланса без перезагрузки, повторный вход и поведение при редизайне сайта.

## 7. Переключение DEMO/REAL

В `main.js` задана таблица маршрутов:

- DEMO: `https://pocketoption.com/ru/cabinet/demo-quick-high-low/`
- REAL: `https://pocketoption.com/ru/cabinet/quick-high-low/RUB/`

При переходе на REAL показывается системное окно подтверждения. После навигации приложение ожидает подтверждения адаптера в течение 20 секунд. Только после подтверждения обновляет выбранный режим.

Маршрут REAL содержит сегмент `RUB`; его корректность и доступность необходимо проверять на конкретном аккаунте и текущей версии Pocket Option. Не считать URL-контракт неизменным.

## 8. Модель состояния

Публичный статус, формируемый `getPublicStatus()`, включает:

- версию приложения и uptime;
- состояние окна сайта (running, visible, loading, url);
- сетевой статус и время проверки;
- диагностический snapshot рыночного потока: число событий/тиков, число активов, число элементов каталога и последние наблюдавшиеся цены (ограниченный список);
- активный тип счёта, баланс, валюту, timestamp и stale-флаг;
- состояние виджета;
- число попыток восстановления;
- состояние updater.

Renderer получает начальное состояние через `getStatus()`, затем обновления через событие `app:status`.

Не следует считать сетевой флаг эквивалентом авторизации или готовности торгового интерфейса.

## 10. Мониторинг и восстановление

Константы:

- `HEALTH_INTERVAL = 30_000` — периодический сетевой/сайтовый health tick;
- `FULL_CHECK_INTERVAL = 5 * 60_000` — исходный интервал полной проверки, далее интервал задаётся настройкой.

Health tick делает запрос к `https://pocketoption.com/` с тайм-аутом 8 секунд. Если сеть недоступна или давно нет сигнала от адаптера, увеличивается счётчик попыток. При достижении порога вызывается `attemptRecovery()`.

Восстановление:

1. Не допускает параллельных запусков.
2. Учитывает историю перезагрузок за последние 10 минут.
3. Прерывает действие при исчерпании лимита.
4. Ожидает заданную задержку.
5. Проверяет доступность сети и существование окна сайта.
6. Перезагружает страницу и записывает событие в журнал.

Это best-effort механизм. Он не восстанавливает недоступность серверной стороны, DNS, блокировки, проснувшийся/уснувший компьютер, истёкшую сессию или необходимость ручной авторизации. Текущий health check также не доказывает доступность торговых операций.

## 11. Полная диагностика

`runFullCheck(source)` формирует список проверок и публикует результат в UI и журнале.

В текущей реализации проверяются:

- готовность процесса Electron;
- каталог пользовательских данных;
- системный трей;
- доступность Pocket Option по сети;
- отзывчивость renderer окна сайта, если оно создано;
- свежесть баланса;
- наличие адаптера;
- health checks загруженных модулей;
- торговое ядро.

Торговое ядро добавляется в результат с `state: 'not-connected'`, `ok: true` и описанием, что оно не подключено в этой сборке. Это информативное состояние, а не тест реального торгового движка.

## 12. Логирование и экспорт

Функция `log(level, message, data)` записывает JSON-объект с ISO timestamp, уровнем, сообщением и необязательными данными в:

`<userData>/logs/application.log`

Формат — JSON Lines. UI читает последние 1000 строк; renderer хранит ограниченный буфер до 1200 событий. Экспорт создаёт ZIP с логом и settings-файлом через `archiver`.

Не записывайте в лог пароли, токены, session cookies, полные персональные данные или содержимое форм авторизации. Проверяйте, не попадают ли чувствительные данные в URL и error payload.

## 13. Система модулей

Менеджер модулей расположен в `modules/manager.js`. При запуске он просматривает подпапки `modules/`, ищет `manifest.json`, пропускает модуль с `enabled: false`, загружает entrypoint и вызывает экспортированную фабрику.

Ожидаемый контракт:

```js
exports.createModule = async context => ({
  async start() {
    // Инициализация модуля
  },
  async healthCheck() {
    return { ok: true, detail: 'Модуль работает' };
  },
  async stop() {
    // Освобождение ресурсов
  }
});
```

Пример manifest:

```json
{
  "id": "sample-module",
  "name": "Sample module",
  "version": "1.0.0",
  "enabled": false,
  "entrypoint": "index.js"
}
```

Правила:

- `id` и `entrypoint` обязательны;
- entrypoint должен оставаться внутри каталога модуля;
- модуль может реализовать `start()`, `healthCheck()`, `stop()`;
- `healthCheck()` должен возвращать объект с `ok` и необязательным `detail`;
- остановка выполняется в обратном порядке загрузки.

**Граница доверия:** модули загружаются как Node.js код в главном процессе. Это фактически полный уровень доверия к установленному модулю. Не загружайте сторонние модули без ревью кода. Механизм не является песочницей.

## 14. Обновления

Используется `electron-updater` с GitHub Releases основного репозитория `Maestro-777/pocket-option-app`. Версия приложения задаётся в `package.json`; версия релиза должна быть выше установленной.

Поведение установленной Windows-сборки:

- автоматическая проверка после запуска (через 12 секунд) и далее каждые 6 часов;
- автопроверка включена по умолчанию и управляется настройкой `autoCheckUpdates`;
- после обнаружения релиза установщик загружается автоматически;
- прогресс, версия и ошибки передаются в renderer через `app:status`;
- после загрузки пользователь может установить обновление кнопкой либо оно установится при следующем штатном выходе (`autoInstallOnAppQuit`);
- в dev-режиме проверки/загрузка отключены, чтобы не показывать ложные ошибки.

Публикация выполняется workflow `.github/workflows/release.yml`: отправка тега `vX.Y.Z` запускает Windows x64 NSIS build и публикацию в GitHub Releases с помощью `GITHUB_TOKEN`. electron-builder формирует установщик и метаданные обновления, включая `latest.yml`.

Релизный чек-лист:
- [ ] Обновить `package.json.version`.
- [ ] Убедиться, что workflow завершился успешно и релиз содержит Setup.exe и `latest.yml` (а также blockmap, если он создан).
- [ ] Установить предыдущую версию на чистую Windows 11 x64.
- [ ] Проверить автоматическое обнаружение и загрузку следующей версии.
- [ ] Проверить установку кнопкой и установку при штатном выходе.
- [ ] Убедиться, что пользовательские данные и persistent session сохранились после обновления.
- [ ] Проверить поведение при отсутствии сети и повторную проверку после восстановления.

До публикации первого релиза и интеграционного теста на Windows механизм нельзя считать полностью подтверждённым. Репозиторий Releases должен быть доступен клиентским установкам; для закрытого репозитория потребуется отдельно спроектировать безопасную авторизацию updater, так как нельзя встраивать PAT в приложение.

## 17. Известные ограничения и технический долг

1. Market Data adapter пока хранит ограниченные буферы только в памяти; данные теряются при перезапуске.
2. Реальные многопарные потоки и история неактивных инструментов ещё не подтверждены.
3. WebSocket tap и межконтекстный мост требуют проверки на реальной сессии Pocket Option и Electron 45. MAIN-world события недоверенные и могут быть подделаны страницей.
4. Интеграция баланса зависит от CSS-селекторов DOM сайта, не от официального API.
5. URL маршрута REAL и сегмент валюты должны быть подтверждены тестом.
6. Нет торгового ядра и автоматического выставления сделок.
7. Нет гарантии фоновой непрерывности сайта при системном сне, throttling ОС, смене сети или серверном сбое.
8. Нет готового проверенного Windows installer в текущем статусе разработки.
9. Нет опубликованного релиза для end-to-end проверки автообновления.
10. Пример модуля выключен по умолчанию.
11. Менеджер модулей исполняет код модулей с полномочиями main process; безопасная изоляция модулей не реализована.
12. Нужны интеграционные тесты и регрессионные проверки после изменений Pocket Option.
13. Текущие проверки синтаксиса и unit-тесты не заменяют ручные испытания на Windows 11.

## 18. Принципы дальнейшего развития

- Сохранять приложение независимым от расширения и торгового ядра, пока интеграция не спроектирована отдельно.
- Не хранить пароль или секреты авторизации в собственных настройках приложения.
- Любые новые IPC-методы проектировать как узкие allowlisted операции.
- Проверять входящие данные и origin/sender.
- Не показывать неподтверждённый баланс как актуальный.
- Сохранять явное подтверждение перехода на REAL.
- Не обозначать неподключённые подсистемы как успешно протестированные.
- Перед выпуском каждой версии обновлять документацию и чек-лист тестирования.
