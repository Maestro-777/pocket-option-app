# Решения и открытые вопросы

## Принятые решения
| ID | Решение |
|---|---|
| D-001 | Основной проект — Electron pocket-option-app; pocket-tracker — вторичный источник примеров. |
| D-002 | Не реализовывать отдельный режим «Только анализ». |
| D-003 | Ручные примеры отделить от сделок и событий бота. |
| D-004 | Поиск общий по исходным OTC-парам, но строго внутри того же таймфрейма. |
| D-005 | Не использовать данные после точки входа в признаках поиска. |
| D-006 | Пауза торговли не останавливает сбор данных и анализ, но блокирует новые сделки. |
| D-007 | Сохранять snapshot параметров каждого решения. |
| D-008 | При нехватке слотов ранжировать по сходству, числу подтверждений, согласованности и исторической результативности. |
| D-009 | Каталог активов не доказывает возможность одновременного исполнения. |
| D-010 | Для сбора входящих WebSocket кадров Electron-прототип использует CDP Network domain, а не позднее внедрение JS-перехватчика в страницу. Решение предварительное до живого теста; при занятом debugger сбор отключается безопасно. |
| D-011 | Рыночный сбор принимает только явно подтверждённые OTC-активы из updateAssets или символы с суффиксом `_OTC`; неоднозначные алиасы без явного OTC-маркера отклоняются. |
| D-012 | Для локального хранения используется встроенный `node:sqlite` без native npm addon. Закрытые свечи и каталог записываются транзакционными пакетами; версия схемы фиксируется `PRAGMA user_version`. Решение зависит от Node runtime Electron и проверяется отдельным Electron smoke test. |
| D-013 | Оперативный рыночный кэш ограничен 300 последними свечами на актив/таймфрейм, чтобы не раздувать RAM и SQLite при круглосуточном потоке. Исторические размеченные примеры обязаны хранить независимые snapshots; глубокая история загружается отдельно. |
| D-014 | Исторические свечи принимаются пассивно из OHLC-событий активного графика. Close-only данные не превращаются в фиктивные OHLC. Активные history-запросы для других пар не отправляются, пока не проверено, что они не переключают торговый инструмент. |
| D-015 | Ручной пример — отдельная сущность SQLite `manual_examples`, не торговая сделка. Он сохраняет собственные input/post candle snapshots; входные признаки проверяются на отсутствие свечей с `endAt > entryAt`. Очистка rolling market cache не должна менять примеры. |
| D-019 | Фоновый scanner реагирует на принятые OTC-тиковые данные, анализирует выбранные таймфреймы при изменении закрытого окна свечей и сохраняет отдельное решение на каждый изменённый срез. Fingerprint учитывает OHLC, параметры и revision пользовательского датасета, чтобы поздние исправления свечей и изменения примеров не пропускались. |
| D-018 | Каждый выполненный ручной Similarity Engine анализ записывается в SQLite `analysis_decisions` вместе с immutable snapshot настроек, совпадений, голосов, входных свечей, причины и версии алгоритма. Автоматический непрерывный scanner и торговые события будут отдельными следующими слоями. |\n| D-017 | Настройки Similarity Engine (Top-N, порог, минимум примеров, голоса, lookback) хранятся в локальном settings.json и валидируются в main process; UI не передаёт их напрямую в файловую систему. |
| D-016 | Первая версия Similarity Engine использует scale-independent OHLC shape features (body/wicks/relative volatility/momentum/gap), weighted mean absolute distance и score 0–100. Score — техническая мера сходства, не вероятность выигрыша; калибровка и веса пока экспериментальные. Сравнение строго в том же таймфрейме, но по общей базе OTC-пар. Пример допускается только если его `entryAt`, `segmentEnd` и срок экспирации уже завершились к моменту анализируемого сигнала. |

## Параметры по умолчанию
- Top-N: 10.
- Минимальное сходство: 80%.
- Минимум совпадений в одном направлении: 6 из 10.
- Максимум одновременных сделок: 1–10, настраиваемо.
- Минимум подходящих примеров не менее 3 обсуждался; правило расчёта требует уточнения.

Все алгоритмические параметры должны быть настраиваемыми. Сходство не равно вероятности выигрыша.

## Предложения, не ставшие обязательными
- Раздельная статистика DEMO и REAL — отдельно не подтверждена.
- Cooldown, max exposure, лимиты по паре/таймфрейму — обсуждались, но не утверждены.
- Формула и веса ранжирования — не согласованы.
- Точные веса факторов ранжирования нескольких одновременных сигналов — не согласованы.

## Открытые технические вопросы
1. Как получать свечи всех OTC-активов одновременно?
2. Можно ли исполнять сделку для неактивного инструмента без переключения DOM?
3. Как атомарно проверить активную пару перед нажатием и подтвердить открытие сделки?
4. Как строить таймфреймы S5–M15 из реального потока?
5. Как хранить большие массивы свечей, разметки, snapshots и журнал?
6. Как точно определять исторический исход с учётом экспирации?
7. Как исключать пересечение обучающих/проверочных выборок по времени?
8. Как калибровать рейтинг без представления его как вероятности выигрыша?
