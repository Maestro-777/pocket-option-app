# Архитектура

## 1. Фактическая архитектура Electron-приложения
- Electron 45.3.4; package version 0.1.1; Windows NSIS x64.
- `main.js`: окна, lifecycle, трей, IPC, настройки, логи, мониторинг/восстановление, обновления, загрузка модулей.
- `preload.js`: ограниченный `window.pocketApp` через contextBridge.
- `site-preload.js`: проверка source/origin и allowlist сообщений сайта перед IPC.
- `site-bridge.js`: DOM-адаптер баланса и типа счёта.
- `renderer/*`: панель и мини-виджет.
- `modules/manager.js`: управление модулями; код модулей исполняется в main process с его полномочиями, это не sandbox.
- Сохранять contextIsolation:true, nodeIntegration:false, sandbox:true и узкий preload API.

## 2. Вторичный pocket-tracker 3.6.0
- Manifest V3 Chrome extension.
- `background.js` — service worker; `inject.js` — MAIN world; `content.js` — isolated UI; bridge-клиент — локальный Windows WebSocket bridge.
- `inject.js` перехватывает WebSocket Pocket Option, обрабатывает Socket.IO JSON/MessagePack, updateAssets, updateStream/quotes, историю и результаты сделок.
- `QuotexCore` анализирует примерно каждые 1.5 секунды; актив синхронизируется из DOM примерно каждые 800 мс.
- `executeTrade()` управляет текущим торговым DOM. Архитектура не доказывает одновременное исполнение по всем парам.

### Рыночные данные
- `market-data-bridge.js` устанавливается в MAIN world через Electron CDP `Page.addScriptToEvaluateOnNewDocument` до выполнения скриптов страницы.
- WebSocket прокси пропускает только allowlist событий: updateAssets, updateStream, quotes/stream и известные события истории.
- Поддерживаются текстовые Socket.IO сообщения и JSON binary attachments.
- `site-preload.js` проверяет source/origin/version/event allowlist и ограничение размера; `main.js` дополнительно проверяет sender и повторно валидирует данные.
- `core/market-data.js` нормализует идентификаторы/время, собирает независимые свечи по активам и 10 таймфреймам, принимает исторические OHLC только при достаточно уверенном определении раскладки.
- Close-only исторические точки не маскируются под OHLC: они проходят как тики.
- Буферы ограничены: до 500 активов, 20 000 тиков на актив, 500 000 тиков суммарно; исторические свечи ограничены 600 на пару/таймфрейм и 100 000 в snapshot.
- `core/market-data-store.js` сохраняет snapshot атомарной заменой файла, восстанавливает его при запуске и периодически сохраняет данные в userData. После восстановления состояние не помечается как live-connected до прихода нового сообщения.

### Разметка и поиск
- `core/example-store.js`: отдельная JSON-база ручных примеров с CRUD, проверкой OHLC, времени, таймфрейма, pre-entry и post-entry данных.
- Путь пользовательской базы: userData/data/examples.json.
- `core/patterns.js`: масштабно-независимые признаки формы свечей, проверка закрытых свечей и защита от данных после точки входа.
- `core/matcher.js`: общая база пар, только тот же таймфрейм, top-N, порог сходства, минимум примеров/голосов, список совпадений и snapshot параметров.
- Сравнение выполняется по одинаковому фиксированному суффиксу свечей. Технический default patternLength=30 настраиваемый; он ещё должен быть проверен на реальных выборках.
- Формула сходства в текущей версии: экспоненциальное преобразование RMSE нормализованных признаков. Это экспериментальный score, не вероятность выигрыша.
- UI: страница «Рыночные данные» и рабочее место «Разметка примеров» с выбором границ участка, точки входа, направления, экспирации, CRUD примеров и просмотром совпадений.

### Решения и журнал
- `core/trading-gate.js`: отдельный контроллер паузы, резервирования сигналов, дедупликации и лимита открытых/ожидающих сделок 1–10. Это пока не исполнитель сделок и не интегрирован с реальным торговым DOM.
- `core/decision-journal.js`: JSONL журнал решений с snapshot параметров и запретом секретоподобных полей.
- Путь журнала: userData/logs/decisions.jsonl.
- IPC API для примеров, свечей и анализа проверяет отправителя; универсальный IPC/file-system API не добавлялся.

## 4. Целевые слои, ещё не завершённые
1. Trade Execution Adapter — безопасное исполнение и подтверждение пары/направления/экспирации.
2. Trade Ledger — фактические сделки и исходы, отдельно от пользовательских разметок.
3. Statistics — доходность, win rate, разрезы по парам/таймфреймам и динамика.
4. Signal scheduler — непрерывный анализ всех доступных OTC-пар и ранжирование конкурирующих сигналов.
5. Validation — хронологический out-of-sample backtest, контроль переобучения и утечки данных.

## 5. Открытые вопросы многопарного режима
Нужно проверить на реальном потоке, действительно ли updateStream содержит все OTC-активы, насколько часто приходят котировки и какие пары доступны. Исторические события могут относиться только к выбранному на сайте инструменту. Не заявлять, что история всех пар загружается одновременно.

Одновременный анализ и одновременное исполнение — разные задачи. Не реализовывать переключение пары и клик как атомарную операцию без подтверждения фактического инструмента.

## 6. Хранение и безопасность
- Настройки, разметки, market-data snapshot и журналы находятся в userData, не в Git.
- Market snapshot и examples используют атомарную запись во временный файл с rename.
- Секреты, пароли, cookies и приватные финансовые данные не сохранять в Git.
- Сообщения MAIN world считать недоверенными, проверять source/origin/schema/size и значения.
