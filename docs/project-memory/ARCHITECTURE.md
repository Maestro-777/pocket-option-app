# Архитектура

## 1. Фактическая архитектура основного приложения
Проверено по main основного репозитория на 2026-11-19.

- Electron 45.3.4; версия package.json 0.1.1; Windows NSIS x64.
- npm run check выполняет node --check перечисленных JavaScript-файлов; это не интеграционные тесты.
- Постоянная сессия Electron: persist:pocket-option-background.
- main.js: главный процесс, окна, lifecycle, трей, IPC, настройки, журналы, мониторинг/восстановление, обновления, загрузка модулей.
- preload.js: ограниченный window.pocketApp через contextBridge и ipcRenderer.invoke.
- site-preload.js: проверяет source/origin, тип сообщения и поля баланса/лога перед IPC.
- site-bridge.js: DOM-адаптер баланса/типа счёта с MutationObserver и периодическим опросом.
- renderer/app.js, index.html, styles.css: интерфейс панели.
- renderer/widget.js/html: мини-виджет.
- modules/manager.js: загрузка, health-check и остановка модулей.
- Код modules/* выполняется в main process с его полномочиями, это не sandbox.

README и руководства прямо указывают, что текущее приложение — оболочка управления окном, сессией, балансом, DEMO/REAL-навигацией, диагностикой, журналами, трей и обновлениями. Автоторговля и торговое ядро не подключены.

## 2. Вторичный pocket-tracker 3.6.0
- Manifest V3 Chrome extension.
- background.js — service worker; inject.js — MAIN world; content.js — isolated content-script UI; bridge-клиент — локальный Windows WebSocket bridge.
- inject.js перехватывает WebSocket Pocket Option, обрабатывает Socket.IO JSON/MessagePack, каталог активов, котировки/свечи и результаты сделок.
- QuotexCore анализирует примерно каждые 1.5 секунды; актив синхронизируется из DOM примерно каждые 800 мс.
- background.js ретранслирует POROBOT_START, POROBOT_STOP, POROBOT_CORE_CMD и BOT_FOCUS_PAIR в указанную или активную вкладку.
- executeTrade() устанавливает сумму и экспирацию и нажимает UP/CALL или DOWN/PUT в текущем торговом DOM.

Архитектурный документ не доказывает одновременное исполнение на всех OTC-парах. Доступность данных многих активов не равнозначна независимому исполнению.

## 3. Целевые архитектурные принципы
Это проектные принципы, не утверждение, что функции уже реализованы.

Слои:
1. Market Data — получение и нормализация котировок/свечей по доступным OTC-инструментам.
2. Candle/Timeframe Engine — построение строго заданных таймфреймов.
3. Annotation Store — пользовательские примеры, CRUD, версионирование и целостность.
4. Feature Extraction — только данные до/включая вход, нормализация относительных движений.
5. Similarity Engine — top-N в общей базе, строго внутри того же таймфрейма.
6. Decision Engine — пороги, подтверждения, ранжирование и причины отказа.
7. Trade Execution Adapter — отдельное исполнение с проверкой актива/направления/экспирации/суммы и подтверждением результата.
8. Trade Ledger & Statistics — журнал решений/сделок и расчёт фактической доходности.
9. UI — разметка, настройки, мониторинг, объяснимые сигналы, журнал и статистика.

Разделение данных:
- Ручные примеры отдельно от сделок.
- Признаки до входа отдельно от пост-входовой оценки.
- Таймфрейм обязателен для выборки.
- Решения и настройки сохраняются как snapshots.
- Решение, включая отказ, должно быть воспроизводимо по данным и версии алгоритма.

## 4. Многопарное исполнение — открытый вопрос
Нужно доказать, какие потоки свечей доступны одновременно, можно ли исполнить сделку по неактивной паре, как безопасно переключать инструмент/вкладки, исключить гонки и подтвердить, что сделка открыта на ожидаемой паре. Не реализовывать быстрые переключения и клики как атомарную операцию без проверки.

## 5. Безопасность Electron
Сохранять contextIsolation:true, nodeIntegration:false, sandbox:true, узкий preload API, проверку IPC sender/origin и строгую валидацию payload. Не добавлять универсальный IPC/filesystem/shell API. Модули в main process — доверенный код. Сообщения MAIN world валидировать по source, origin, типу и схеме.

## 6. Хранение
Настройки и журналы сейчас в Electron userData. Формат/СУБД для свечей, разметок, snapshots и сделок ещё не выбраны. Требуется сравнение, план миграций, backup/restore и атомарные операции до внедрения.


## 7. Прототип Market Data adapter (ветка feature/market-data-adapter)

Добавлен экспериментальный data-only путь получения рыночных событий:

- `site-preload.js` на document-start устанавливает наблюдатель WebSocket в MAIN world через `webFrame.executeJavaScript`.
- Наблюдатель не отправляет команды Pocket Option, не меняет торговые элементы и не выполняет сделки.
- Разрешённые события: `updateAssets`, `updateStream`, `quotes/stream`, `updateHistoryNewFast`, `updateHistoryNew`, `loadHistoryPeriod`, `loadHistoryPeriodFast`, `history/list/v2`.
- События пакетируются и проходят через `window.postMessage` → `site-preload.js` → IPC `site:market-batch` → `MarketDataStore` в main process.
- `core/market-data.js` нормализует имена активов, секундные/миллисекундные timestamps, тики и OHLC-историю; хранит ограниченные буферы отдельно по активам и периодам.
- Main process проверяет отправителя, allow-list событий, размер и частоту IPC batch через core/ipc-validation.js. Тот же модуль проверяет свежесть/частоту balance payload и HTTPS origin allow-list. Сообщения MAIN world остаются недоверенными данными; они не являются источником команд.

Ограничения прототипа:
- Буферы пока находятся только в памяти и теряются при перезапуске.
- Каталог активов и факт наличия нескольких тик-потоков не доказывают доступность полной истории или исполнение по неактивной паре.
- Инжектор и межконтекстный мост ещё не проверены на реальной сессии Pocket Option в Electron 45 / Windows.
- Не подключены анализ, Decision Engine и торговое исполнение.


Дополнительно: core/ipc-validation.js содержит чистые валидаторы origin, баланса и batch payload; они покрыты node:test. Это unit-level проверка контракта, не полноценный тест Electron sender/webContents.
