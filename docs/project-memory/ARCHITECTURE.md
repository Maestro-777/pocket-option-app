# Архитектура

Последнее обновление: 2026-11-20. Этот документ разделяет фактически реализованные модули, ограничения прототипа и ещё не реализованные целевые слои.

## 1. Основное Electron-приложение

- Electron 45.3.4; версия package.json 0.1.1; Windows NSIS x64.
- `npm run check` — синтаксическая проверка JavaScript-файлов.
- `npm test` — модульные тесты через `node:test`.
- Windows CI запускает проверки, unit tests, Electron runtime smoke test и сборку установщика.
- Постоянная сессия Electron: `persist:pocket-option-background`.
- `main.js`: главный процесс, окна, lifecycle, трей, IPC, настройки, журналы, мониторинг/восстановление, обновления, загрузка модулей.
- `preload.js`: ограниченный `window.pocketApp` через contextBridge и `ipcRenderer.invoke`.
- `site-preload.js`: в изолированном preload world читает DOM баланса/типа счёта, нормализует значения и напрямую отправляет ограниченные IPC-события. Main-world `window.postMessage` мост удалён, чтобы страница не могла напрямую подделывать привилегированные сообщения.
- `site-bridge.js`: удалён как небезопасный main-world адаптер.
- `renderer/app.js`, `index.html`, `styles.css`: интерфейс панели.
- `renderer/widget.js/html`: мини-виджет.
- `modules/manager.js`: загрузка, health-check и остановка модулей.
- `renderer/labeler.html/js/css`: отдельное окно ручной разметки, выбора OTC-пары и таймфрейма, Canvas-график, отметки участка и intrabar-точки входа, CRUD независимых примеров, поиск совпадений, walk-forward проверка и журнал решений.
- `modules/*` выполняются в main process с его полномочиями, это не sandbox.

## 2. Market Data pipeline

- `core/timeframes.js`: десять допустимых таймфреймов S5, S10, S15, S30, M1, M2, M3, M5, M10, M15.
- `core/candle-series.js`: инкрементальный OHLC по одному активу/таймфрейму, коррекция сохранённых свечей поздними тиками и ограничение памяти.
- `core/market-data.js`: распределение тиков по независимым сериям; очередь dirty-свечей, ревизии для безопасного подтверждения записи, backpressure и восстановление из SQLite. Если поздний тик вышел за retention короткого таймфрейма, но ещё допустим для длинного, длинная серия всё равно обновляется.
- `core/pocketoption-protocol.js`: разбор Socket.IO текстовых кадров и бинарных UTF-8 JSON attachments; нормализация `updateStream`, `quotes/stream` и OHLC-истории из `updateHistoryNewFast`, `loadHistoryPeriod`, `history/list/v2`. Для live-форматов без timestamp используется время получения кадра; malformed timestamps не подменяются.
- `core/asset-catalog.js`: чтение `updateAssets`, нормализация символов, определение OTC по явному маркеру символа/названия и отказ от неоднозначных alias.
- `core/market-data-capture.js`: CDP Network capture через Electron `webContents.debugger`, отдельный декодер на каждый WebSocket, передача принятых OTC-тиков в MarketDataHub.
- `main.js` подключает CDP capture к окну Pocket Option; приложение не внедряет произвольный обработчик в JS-контекст сайта.

### Поток данных

1. Pocket Option отправляет Socket.IO события.
2. CDP получает входящие WebSocket frames.
3. PocketOptionProtocol разбирает event и tick/history payload.
4. AssetCatalog определяет, подтверждён ли актив как OTC.
5. MarketDataHub строит отдельные OHLC серии по каждому активу и таймфрейму.
6. Завершённые свечи сохраняются в SQLite пакетами; незавершённые свечи не считаются входными признаками.
7. Принятый тик ставит актив в очередь DecisionScanner.

Ограничения прототипа:
- Лимит MarketDataHub: до 150 активов и до 1000 свечей на актив/таймфрейм в RAM; SQLite хранит rolling историю до 1000 свечей на серию.
- Исторические OHLC кадры пассивно принимаются из событий активного графика. Price-only history (формат `[timestamp, price]`, который также встречается в `pocket-tracker`) намеренно не превращается в OHLC свечи, поскольку high/low из него неизвестны. Это не гарантирует глубокую историю для всех пар одновременно.
- Сбор всех пар зависит от фактического состава `updateStream`/ `quotes/stream`, который отдаёт сервер.
- CDP capture требует свободного debugger target. Если отладчик уже подключён, сбор помечается unavailable; чужое подключение не отключается.
- Живой end-to-end тест на текущем сайте Pocket Option и Windows машине ещё не подтверждён.

## 3. SQLite и модели данных

- `core/market-data-store.js`: встроенный `node:sqlite`, schema version 5: таблицы `market_candles`, `asset_catalog`, `manual_examples`, `analysis_decisions`, `trade_results`. `trade_results` хранит наблюдаемые брокерские закрытия с idempotency key и даёт агрегаты P/L/баланса по измерениям.
- `normalizeTradeResults` в `core/pocketoption-protocol.js` разбирает `successcloseOrder` и legacy close events; `MarketDataCapture` передаёт их в SQLite через `onTradeResult`. Время/пара/TF/направление/счёт могут быть неизвестны, если брокер не прислал соответствующие поля.
- Таблицы включают rolling OHLC candles, asset catalog, независимые `manual_examples` и `analysis_decisions`.
- Ручной пример сохраняет отдельные snapshots до входа и после входа. Ручная разметка не является сделкой и не переписывается алгоритмом.
- `analysis_decisions` хранит сигнал или отказ, причину, настройки, найденные совпадения, голоса, query candle snapshot и версию алгоритма.
- Decision journal — append-only для решений; последующие изменения настроек или примеров не должны менять уже сохранённый snapshot.
- SQLite работает в main process через синхронный `DatabaseSync`; операции пакетируются. Нагрузку на живом потоке нужно проверить.

## 4. Similarity Engine

- `core/similarity-engine.js`: извлечение scale-independent OHLC shape features, сравнение top-N, подсчёт голосов направления и исторической результативности.
- Сравнение строго внутри одного таймфрейма, но между разными OTC-парами.
- Признаки используют форму тела/теней, относительную волатильность, импульс и гэп, а не абсолютную цену.
- Используются только закрытые непрерывные свечи до входа. Окна с пропусками не сравниваются.
- Исторический пример допускается в момент анализа только после завершения его segmentEnd и экспирации; это защищает walk-forward проверку от будущего outcome leakage.
- По умолчанию: Top-10, порог 80%, минимум 3 подходящих примера, 6 голосов за направление, lookback 30 свечей. Настройки сохраняются локально и доступны для изменения.
- 80% — экспериментальная мера структурного сходства, а не вероятность выигрыша. Нужна калибровка на реальной выборке.
- `prepareExamples` предварительно вычисляет признаки; DecisionScanner кэширует их до изменения набора примеров/настроек.
- `evaluateWalkForward` выполняет хронологическую проверку по более ранним, уже завершившимся примерам; отчёт показывает точность среди сигналов и покрытие.

## 5. Фоновый DecisionScanner

- `core/decision-scanner.js`: event-driven scanner, получает уведомление о принятом OTC-тике, ставит актив в очередь и анализирует выбранные таймфреймы.
- По умолчанию включены все десять таймфреймов; пользователь может выбрать один или несколько в окне разметки.
- Решение создаётся при изменении закрытого окна свечей. Fingerprint учитывает OHLC, настройки и revision пользовательского датасета: поздняя коррекция свечи, изменение примеров или настроек вызывает повторный анализ.
- Сканер предотвращает повторную запись одного и того же решения для неизменённого окна. Это не является защитой от повторного торгового входа.
- Все сигналы и причины отказа записываются в SQLite.
- `core/signal-ranking.js`: детерминированное ранжирование актуальных сигналов по лексикографическому порядку: сходство, голоса, согласованность, историческая результативность. Список до 50 свежих кандидатов доступен через status API и отображается в окне разметки.
- `core/trade-coordinator.js`: чистая функция `planTradeIntents` проверяет pause/disabled, лимит 1–10, ранжирует кандидатов и блокирует повторный вход на ту же пару/таймфрейм/бар, даже если направление пересмотрено. Это пока не связано с реальным ledger открытых сделок и не отправляет ордера.

## 6. Вторичный репозиторий pocket-tracker 3.6.0

- Manifest V3 Chrome extension.
- `background.js` — service worker; `inject.js` — MAIN world; `content.js` — isolated content-script UI; bridge-клиент — локальный Windows WebSocket bridge.
- `inject.js` перехватывает WebSocket Pocket Option. Текстовые Socket.IO кадры содержат JSON; фактическая функция `decodePOBinary` декодирует бинарные кадры как UTF-8 JSON, а не MessagePack.
- `updateStream` и `quotes/stream` могут содержать тики нескольких активов в одном событии. `updateAssets` содержит каталог активов.
- `QuotexCore` анализирует примерно каждые 1.5 секунды; актив синхронизируется из DOM примерно каждые 800 мс.
- `background.js` ретранслирует `POROBOT_START`, `POROBOT_STOP`, `POROBOT_CORE_CMD` и `BOT_FOCUS_PAIR` в указанную или активную вкладку.
- `executeTrade()` устанавливает сумму и экспирацию и нажимает UP/CALL или DOWN/PUT в текущем торговом DOM. Это не доказывает одновременное исполнение на разных парах.

## 7. Целевые слои и текущая готовность

1. Market Data — реализован прототип сбора/нормализации OTC данных; живой охват пар не подтверждён.
2. Candle/Timeframe Engine — реализован и покрыт unit tests.
3. Annotation Store — реализованы SQLite CRUD и snapshots; живой UX требует проверки.
4. Feature Extraction — реализована первая версия, только закрытые pre-entry свечи.
5. Similarity Engine — реализована первая версия, требуется калибровка на пользовательских данных.
6. Decision Engine — реализован фоновый scanner и причины отказа; ranking helper формирует список кандидатов, но пока не распределяет торговые слоты.
7. Trade Execution Adapter — не реализован в Electron; trade intent planner реализован, но не подключён к live scanner. Multi-pair исполнение остаётся открытым архитектурным вопросом.
8. Trade Ledger & Statistics — журнал решений реализован; фактический ledger сделок и статистика P/L не реализованы.
9. UI — ручная разметка и анализ реализованы; торговые настройки, исполнение и P/L UI не завершены.

## 8. Многопарное исполнение — архитектурное направление подтверждено, реализация ещё открыта

Официальный Pocket Option Blog описывает multi-chart режим на 2–4 графика и возможность использовать отдельные browser tabs для нескольких инструментов: https://pocketoption.com/blog/en/product-guides/how-to-read-pocket-option-charts/. Официальное соглашение допускает любое количество одновременно открытых операций, но суммарный объём новых операций не должен превышать баланс: https://pocketoption.com/en/public-offer/ (раздел Trading Operations Execution).

Это подтверждает, что multi-pair execution можно проектировать через несколько отдельных chart contexts/tabs, а не пытаться кликать разные пары в одном DOM. Но текущий `pocket-tracker` `executeTrade()` всё ещё нажимает кнопки текущего активного DOM. Нужно реализовать и проверить управление отдельными Electron BrowserWindow/webContents в общей persistent session, надёжное определение пары в каждом окне, выбор свободного окна и подтверждение фактической сделки. Multi-chart может быть ограничен 2–4 графиками; отдельные tabs — более вероятный путь к лимиту 1–10 одновременных сделок.

**Условие до live/REAL исполнения:** текущая официальная публичная оферта указывает, что результаты операции могут быть отменены или пересмотрены, если операция выполнена с помощью неавторизованного bot software (раздел Trading Operations Execution). Нельзя считать автоматическую торговлю разрешённой только потому, что она технически возможна. До включения REAL необходимо отдельно проверить актуальные условия и разрешённость такого способа использования аккаунта.

## 9. Безопасность Electron

Сохранять `contextIsolation:true`, `nodeIntegration:false`, `sandbox:true`, узкий preload API, проверку IPC sender/origin и строгую валидацию payload. Не добавлять универсальный IPC/filesystem/shell API. Сообщения MAIN world валидировать по source, origin, типу и схеме.

## 10. Хранение и восстановление

Настройки, журналы, rolling свечи, каталог, ручные примеры и решения находятся в Electron userData. Нужны backup/restore, миграционные тесты и проверка поведения при аварийном завершении. Секреты, пароли, токены и cookies в проектную память и логи не записывать.
