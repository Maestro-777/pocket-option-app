# Архитектура

## 1. Фактическая архитектура основного приложения
Проверено по main основного репозитория на 2026-11-19.

- Electron 45.3.4; версия package.json 0.1.1; Windows NSIS x64.
- npm run check выполняет node --check перечисленных JavaScript-файлов; это не интеграционные тесты. npm test запускает node:test.
- Постоянная сессия Electron: persist:pocket-option-background.
- main.js: главный процесс, окна, lifecycle, трей, IPC, настройки, журналы, мониторинг/восстановление, обновления, загрузка модулей.
- preload.js: ограниченный window.pocketApp через contextBridge и ipcRenderer.invoke.
- site-preload.js: проверяет source/origin, тип сообщения и поля баланса/лога перед IPC.
- site-bridge.js: DOM-адаптер баланса/типа счёта с MutationObserver и периодическим опросом.
- renderer/app.js, index.html, styles.css: интерфейс панели.
- renderer/widget.js/html: мини-виджет.
- modules/manager.js: загрузка, health-check и остановка модулей.
- core/timeframes.js: 10 допустимых таймфреймов и пакетная агрегация.
- core/candle-series.js: инкрементальный OHLC по одному активу/таймфрейму, коррекция сохранённых свечей поздними тиками и ограничение памяти.
- core/market-data.js: распределение каждого тика по десяти независимым сериям актива; ограничение числа активов и числа свечей в памяти.
- core/pocketoption-protocol.js: разбор Socket.IO текстовых кадров и бинарных UTF-8 JSON attachments; нормализация updateStream/quotes/stream и OHLC-истории из updateHistoryNewFast/loadHistoryPeriod/history/list/v2.
- core/asset-catalog.js: чтение updateAssets, нормализация символов, определение OTC по явному маркеру символа/названия и отказ от неоднозначных alias.
- core/market-data-capture.js: изолированный CDP Network capture через Electron webContents.debugger, отдельный декодер на каждый WebSocket.
- core/market-data-store.js: SQLite-хранилище свечей, каталога и независимых ручных примеров через встроенный `node:sqlite`; транзакционные upsert, CRUD, контроль целостности и восстановление.
- main.js подключает CDP capture к окну Pocket Option и публикует статус/диагностику рыночного потока.
- Код modules/* выполняется в main process с его полномочиями, это не sandbox.

README и руководства прямо указывают, что текущее приложение — оболочка управления окном, сессией, балансом, DEMO/REAL-навигацией, диагностикой, журналами, трей и обновлениями. Автоторговля и торговое ядро не подключены.

## 2. Вторичный pocket-tracker 3.6.0
- Manifest V3 Chrome extension.
- background.js — service worker; inject.js — MAIN world; content.js — isolated content-script UI; bridge-клиент — локальный Windows WebSocket bridge.
- inject.js перехватывает WebSocket Pocket Option. Текстовые Socket.IO кадры содержат JSON; комментарий decodePOBinary и фактический код показывают, что бинарные кадры декодируются как UTF-8 JSON, а не MessagePack.
- updateStream и quotes/stream могут содержать тики нескольких активов в одном событии. updateAssets содержит каталог активов.
- В текущем Electron-прототипе CDP Network domain используется для чтения входящих WebSocket кадров без внедрения обработчика в JS-контекст сайта.
- QuotexCore анализирует примерно каждые 1.5 секунды; актив синхронизируется из DOM примерно каждые 800 мс.
- background.js ретранслирует POROBOT_START, POROBOT_STOP, POROBOT_CORE_CMD и BOT_FOCUS_PAIR в указанную или активную вкладку.
- executeTrade() устанавливает сумму и экспирацию и нажимает UP/CALL или DOWN/PUT в текущем торговом DOM.

Архитектурный документ не доказывает одновременное исполнение на всех OTC-парах. Доступность данных многих активов не равнозначна независимому исполнению.

## 3. Текущий прототип Market Data (не считать production-ready)
- MarketDataCapture подключает Chromium DevTools Protocol к `siteWindow.webContents.debugger` и слушает `Network.webSocketFrameReceived`.
- На каждый CDP `requestId` создаётся отдельный `PocketOptionProtocol`, чтобы бинарный attachment одного сокета не перепутался с событием другого.
- Декодер поддерживает наблюдаемые в `pocket-tracker` 3.6.0 события `updateStream`, `quotes/stream` и `updateAssets`; время в секундах преобразуется в миллисекунды, миллисекунды остаются без изменения.
- `updateAssets` формирует AssetCatalog. В MarketDataHub допускаются только активы, которые каталог или явный суффикс `_OTC` подтверждает как OTC. Если базовый символ соответствует и обычному, и OTC-инструменту, тик без явного суффикса отклоняется как неоднозначный.
- MarketDataHub направляет каждый тик в отдельные серии S5, S10, S15, S30, M1, M2, M3, M5, M10 и M15; ведёт очередь dirty-свечей, подтверждение записанных ревизий и backpressure при переполнении очереди.
- Закрытые свечи и каталог сохраняются в `userData/market-data.sqlite` транзакционными пакетами примерно раз в секунду; незакрытые свечи не записываются. При старте загружаются последние 300 свечей по каждому активу/таймфрейму. Старые строки рыночного кэша удаляются, поэтому отдельные пользовательские примеры должны хранить собственные снимки данных.
- SQLite работает в main process через синхронный `DatabaseSync`; операции пакетируются. Нужно проверить нагрузку на живом потоке.
- Текущие лимиты прототипа: до 150 активов и до 300 последних свечей на актив/таймфрейм в RAM и SQLite; SQLite очищается до этого лимита раз в минуту. Переполнение лимита активов отклоняется явно, без молчаливого удаления.
- Данные хранятся только в оперативной памяти текущего процесса. Перезапуск приложения очищает их; долговременное хранилище, каталог OTC и загрузка исторических свечей ещё не реализованы.
- CDP capture требует свободного debugger target. Если отладчик уже подключён, сбор помечается `unavailable`, чужое подключение не отключается.
- Исторические OHLC-кадры пассивно принимаются из событий активного графика; close-only payload без OHLC намеренно пропускается.
- История пока не запрашивается активно для всех пар: текущий источник — события, которые сам сайт отправляет для открытого/выбранного инструмента.
- Реальная совместимость CDP с текущей версией сайта ещё не подтверждена живым тестом на Windows.
- `node:sqlite` в Node 24.22.3 имеет статус Release Candidate по документации Node.js; добавлен отдельный smoke test внутри Electron, результат Windows CI требуется проверить.

## 4. Целевые архитектурные принципы
Это проектные принципы, не утверждение, что функции уже реализованы.

Слои:
1. Market Data — получение и нормализация котировок/свечей по доступным OTC-инструментам.
2. Candle/Timeframe Engine — построение строго заданных таймфреймов.
3. Annotation Store — пользовательские примеры, CRUD, версионирование и целостность.
4. Feature Extraction — только данные до/включая вход, нормализация относительных движений.
5. Similarity Engine — top-N в общей базе, строго внутри того же таймфрейма.
6. Decision Engine — пороги, подтверждения, ранжирование и причины отказа.
7. Trade Execution Adapter — отдельное исполнение с проверкой актива/направления/экспирации/суммы и подтверждением результата.
8. Trade Ledger & Statistics — журнал решений/сделок и расчёт фактической доходности.
9. UI — разметка, настройки, мониторинг, объяснимые сигналы, журнал и статистика.

Разделение данных:
- Ручные примеры отдельно от сделок.
- Признаки до входа отдельно от пост-входовой оценки.
- Таймфрейм обязателен для выборки.
- Решения и настройки сохраняются как snapshots.
- Решение, включая отказ, должно быть воспроизводимо по данным и версии алгоритма.

## 5. Многопарное исполнение — открытый вопрос
Нужно доказать, какие потоки свечей доступны одновременно, можно ли исполнить сделку по неактивной паре, как безопасно переключать инструмент/вкладки, исключить гонки и подтвердить, что сделка открыта на ожидаемой паре. Не реализовывать быстрые переключения и клики как атомарную операцию без проверки.

## 6. Безопасность Electron
Сохранять contextIsolation:true, nodeIntegration:false, sandbox:true, узкий preload API, проверку IPC sender/origin и строгую валидацию payload. Не добавлять универсальный IPC/filesystem/shell API. Модули в main process — доверенный код. Сообщения MAIN world валидировать по source, origin, типу и схеме.

## 7. Хранение
Настройки и журналы сейчас в Electron userData. Формат/СУБД для свечей, разметок, snapshots и сделок ещё не выбраны. Требуется сравнение, план миграций, backup/restore и атомарные операции до внедрения.
